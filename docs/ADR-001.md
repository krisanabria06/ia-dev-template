# ADR-001 — Estrategia de paginación del historial de transacciones

## Estado

Propuesta, pendiente de validar contra el PRD y el modelo de datos.

## Contexto

El historial de transacciones debe consultarse por comercio y devolver resultados paginados. El volumen esperado, los filtros definitivos y los tiempos objetivo no están definidos; no se inventan en este documento.

## Alternativas consideradas

1. **Offset/limit:** simple de implementar y permite ir a una página numerada, pero puede degradarse al avanzar muchas páginas y ser inestable si los datos cambian entre consultas.
2. **Cursor/keyset:** aplica un cursor sobre un orden estable y evita recorrer páginas anteriores, pero requiere definir ese orden y adaptar la navegación.
3. **Materialización o caché:** puede reducir el costo de consultas repetidas, pero agrega infraestructura y no está justificado por la información disponible.

## Decisión

Adoptar cursor/keyset como propuesta para la consulta del historial, aplicando primero los filtros autorizados y después el cursor sobre un orden reproducible. `created_at` y el formato del cursor quedan sujetos a confirmación; mientras tanto, esta decisión no autoriza a agregar esos campos al modelo.

La API debe validar identidad, comercio, filtros y parámetros de paginación antes de invocar el caso de uso. La respuesta debe incluir los datos de la página y, cuando corresponda, un cursor para continuar.

## Consecuencias positivas

- Reduce el trabajo repetido al avanzar por un historial grande.
- Favorece resultados más consistentes cuando se agregan transacciones entre páginas.
- Mantiene la paginación dentro del caso de uso y el repositorio, sin servicios externos.

## Consecuencias negativas

- La implementación es más compleja que `offset/limit`.
- No permite naturalmente saltar a una página numerada.
- Depende de un orden estable, índices adecuados y un formato de cursor que todavía deben definirse.
- Puede requerir cambios en el cliente y en el modelo de datos si las preguntas abiertas se resuelven de forma incompatible.

## Preguntas abiertas y evidencia pendiente

- ¿El PRD confirma cursor/keyset o requiere navegación por número de página?
- ¿Existe `created_at` y es confiable para ordenar?
- ¿Qué filtros y límite máximo se deben soportar?
- ¿Qué reglas definen que un usuario puede consultar un comercio?
- ¿Qué índices y volumen de datos tendrá la base de datos?

## Revisión

Revisar esta decisión cuando se confirme el PRD, el modelo de transacción y una medición con datos representativos.
